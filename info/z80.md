# Z80 CPU Documentation

This document provides a language-independent architectural guide for building a Z80 CPU emulator. It is based on the Rust implementation in [src/z80.rs](../src/z80.rs), and is designed to be complete enough that you can implement a fully compatible emulator from scratch in any programming language (e.g., C, C++, Rust, Python, Go, Java, C#).

## Overview

The CPU should be implemented as a state machine (a class, struct, or module). The core interface should expose at least:

- `init(mmu, port_writer, port_reader)` — initializes the CPU with memory and I/O callbacks.
- `initialize()` — sets a deterministic emulator construction state, then applies hardware reset.
- `step(runFor)` — runs instructions, deducting their cycle cost from `runFor`, and returns the actual cycles consumed.
- `irq()` — triggers an interrupt (IM 1 only in this implementation).
- `reset()` — applies the Z80 hardware reset state. Only PC, interrupt state, I, R, and HALT are defined by reset; other CPU registers retain their current contents.
- `getReg(name)` / `setReg(name, val)` — optional register accessors for debugging.

The MMU must provide at minimum:
- `r8(addr)` / `w8(addr, val)` — 8-bit memory access.
- `r16(addr)` / `w16(addr, val)` / `w16reverse(addr, val)` — 16-bit memory access (little-endian).
- `r8s(addr)` — signed 8-bit read (for displacements).

Port callbacks:
- `port_writer(port, val, expectedval)` — OUT.
- `port_reader(port, expectedval)` — IN.

## Register File

Registers can be stored using native 16-bit and 8-bit variables. The Z80 pairs two 8-bit registers to form one 16-bit register (e.g., `B` and `C` form `BC`, where `B` is the high byte and `C` is the low byte).

```text
16-bit Register   8-bit High / Low
----------------------------------
PC                (Program Counter)
SP                (Stack Pointer)
IR                I (Interrupt) / R (Refresh)
AF                A (Accumulator) / F (Flags)
BC                B / C
DE                D / E
HL                H / L
IX                IXh / IXl
IY                IYh / IYl

Shadow Registers:
AF'               A' / F'
BC'               B' / C'
DE'               D' / E'
HL'               H' / L'
```

**Implementation Strategy:** 
- In C/C++, you can use a `union` (assuming a little-endian host) to automatically alias the 8-bit and 16-bit registers.
- In languages like Java, C#, or Python, you can store either the 8-bit registers or the 16-bit registers as the source of truth, and provide getters/setters for the other. For example, storing `H` and `L` as 8-bit integers, and computing `HL = (H << 8) | L`. When writing to `HL`, `H = (val >> 8) & 0xFF` and `L = val & 0xFF`.

**Initialization values:**
- `SP = 0xFFFF`
- `AF, BC, DE, HL, IX, IY = 0xFFFF`
- `AF', BC', DE', HL' = 0xFFFF`
- Then hardware reset is applied.

**Hardware reset values:**
- `PC = 0x0000`
- `I = 0x00`, `R = 0x00`
- `halted = 0`, `im = 0`, `IFF1 = 0`, `IFF2 = 0`
- Other registers, including `SP`, are not hardware-defined by reset. `reset()` leaves their current contents unchanged.

## Flags

The F register uses these bit masks:

| Bit | Mask | Name | Meaning |
|-----|------|------|---------|
| 7   | 0x80 | S    | Sign (copy of bit 7) |
| 6   | 0x40 | Z    | Zero |
| 5   | 0x20 | 5    | Undocumented bit 5 (copy of bit 5 of result) |
| 4   | 0x10 | H    | Half-carry |
| 3   | 0x08 | 3    | Undocumented bit 3 (copy of bit 3 of result) |
| 2   | 0x04 | P/V  | Parity/Overflow |
| 1   | 0x02 | N    | Add/Subtract (0 = add, 1 = sub) |
| 0   | 0x01 | C    | Carry |

Parity rule: even number of 1 bits = P/V set (1), odd = P/V clear (0).

## Lookup Tables

Two 256-entry lookup tables should be precomputed at startup to avoid recomputing flags dynamically during execution:

- **SZ53table[byte]** = Contains the Sign (S), Zero (Z), and undocumented 5 and 3 flags.
- **SZ53Ptable[byte]** = Same as `SZ53table`, but with the Parity (P/V) flag added.

**Generation Pseudo-code:**
```text
SZ53table = array of 256 bytes
SZ53Ptable = array of 256 bytes

for i from 0 to 255:
    // Extract S (bit 7), 5 (bit 5), and 3 (bit 3) directly from the value
    flags = (i & 0x80) | (i & 0x20) | (i & 0x08)
    
    // Set Zero flag if value is 0
    if i == 0:
        flags |= 0x40
        
    SZ53table[i] = flags
    
    // Calculate Parity (even parity = 1, odd parity = 0)
    parity = 0
    temp = i
    while temp > 0:
        parity ^= (temp & 1)
        temp >>= 1
        
    SZ53Ptable[i] = flags
    if parity == 0:
        SZ53Ptable[i] |= 0x04  // Set P/V flag for even parity

// Special case: 0 has both Zero and Even Parity
```

These are used by most 8-bit arithmetic and logical instructions.

## Core Execution Loop

`step(runFor)` loops while `runFor >= 0`. Each iteration is one instruction:

### 1. Opcode Fetch

Read the byte at `PC`. Handle prefixes:

- **DD / FD prefix loop:**
  - If the first byte is `0xDD` or `0xFD`, read the next byte.
  - If the next byte is also `0xDD` or `0xFD`, treat the earlier prefix as a 4-cycle NOP and keep consuming.
  - Once a non-prefix byte is found, combine into a 16-bit opcode key: `(prefix << 8) | byte`.
  - If the key is `0xDDCB` or `0xFDCB`, read a signed displacement at `PC+2` and a fourth byte at `PC+3`, forming a 24-bit key `(0xDDCB << 8) | byte4`.
  - Otherwise it's a regular `DDxx` / `FDxx` instruction.
- **CB / ED prefix:**
  - Combine with the next byte into a 16-bit key `(0xCB << 8) | byte2` or `(0xED << 8) | byte2`.

Track `rAdd` = number of opcode bytes consumed (used to update the R register).

### 2. R Register Update

```text
R = (R & 0x80) | ((R + rAdd) & 0x7F)
```

Bit 7 is preserved; the low 7 bits increment by the number of bytes fetched.

### 3. Opcode Dispatch

Look up the key in your `opcode_table`.

- If not found and it was a `DD`/`FD` prefixed instruction that isn't explicitly defined, fall back to the base opcode (`opcode & 0xFF`) and add 4 cycles (`tAdd`). This is how undocumented `DD`/`FD` behavior is handled for most opcodes (they act like NOPs for the prefix).
- If still not found, throw "not implemented".

### 4. Execute

Execute the opcode logic. The opcode handler should output or update:

- `cycles` — instruction cycle time.
- `length` — instruction byte length (used to advance PC).
- *Optional:* Operands (useful for disassembly or debugging).

### 5. Advance PC

If `length > 0` and the CPU is not halted:

```text
PC = PC + length
```

`HALT` is the exception: the PC advances past the HALT opcode before the CPU enters the halted state, so an accepted interrupt returns to the following instruction.

Jump instructions set `length = 0` and directly assign `PC` inside the opcode handler.

### 6. Timing

```text
instrTime = cycles + tAdd
runFor -= instrTime
actRuntime += instrTime
```

Return the accumulated `actRuntime`.

### Timing Model Notes

Z80 timing is counted in **T-states** (clock periods). Instructions are built from **M-cycles** (machine cycles), such as opcode fetch, memory read/write, I/O read/write, and interrupt acknowledge. The emulator normally stores the final instruction T-state count directly in each opcode handler, but these rules explain where those numbers come from and how to sanity-check new instructions:

| Cycle kind | Typical T-states | Notes |
|---|---:|---|
| Opcode fetch (`M1`) | 4 | Fetches the opcode byte and performs refresh during T3/T4. |
| Extra prefix byte fetch | 4 | `CB`, `ED`, `DD`, and `FD` prefix bytes are opcode fetch-style cycles. Repeated `DD`/`FD` prefixes add 4 T-states each. |
| Memory read/write | 3 | Used for immediate bytes, absolute address bytes, stack bytes, and normal memory operands. |
| I/O read/write | 4 | Z80 automatically inserts one wait state for I/O cycles, so these are longer than memory cycles. |
| Interrupt acknowledge | 7 | Special `M1` cycle with two automatic wait states. Additional stack writes make IM 1 interrupt entry 13 T-states in this emulator. |
| Internal operation | varies | Extra ALU/addressing/refresh work not visible as a bus transfer; often the difference between the bus-cycle sum and the documented timing. |

Practical calculation examples:

```text
NOP                 = opcode fetch
                    = 4

LD r,n              = opcode fetch + immediate memory read
                    = 4 + 3 = 7

LD (HL),n           = opcode fetch + immediate read + memory write
                    = 4 + 3 + 3 = 10

LD r,(HL)           = opcode fetch + memory read
                    = 4 + 3 = 7

JP nn               = opcode fetch + two immediate reads
                    = 4 + 3 + 3 = 10

CALL nn             = opcode fetch + two immediate reads + two stack writes + internal cycle
                    = 4 + 3 + 3 + 3 + 3 + 1 = 17

IN r,(C)            = ED prefix fetch + opcode fetch + I/O read
                    = 4 + 4 + 4 = 12
```

Indexed instructions add prefix and displacement work:

```text
LD r,(IX+d)         = DD fetch + opcode fetch + displacement read + indexed memory read + address overhead
                    = 4 + 4 + 3 + 3 + 5 = 19

LD (IX+d),n         = DD fetch + opcode fetch + displacement read + immediate read + indexed memory write + overhead
                    = 4 + 4 + 3 + 3 + 3 + 2 = 19

DD CB d op          = DD fetch + CB fetch + displacement read + final opcode fetch + indexed read/write/bit work
                    = 20 for BIT, 23 for rotate/shift/RES/SET
```

Conditional instructions have two timings when the taken and not-taken paths do different bus work:

```text
JR cc,e             = 12 if taken, 7 if not taken
DJNZ e              = 13 if taken, 8 if not taken
CALL cc,nn          = 17 if taken, 10 if not taken
RET cc              = 11 if taken, 5 if not taken
```

Wait states can lengthen real hardware cycles through the `WAIT` line. This emulator currently uses fixed documented T-state counts and does not model external wait-state insertion.

## Arithmetic Helpers

All arithmetic is factored into shared helper functions that take inputs and write to a 2-element result array `resOut = [result_byte, flags_byte]`.

### add8(val1, val2, CIn, resOut)

```
res = val1 + val2 + CIn
res4 = (val1 & 0x0F) + (val2 & 0x0F) + CIn
res8 = res & 0xFF
overflow = (sign(val1) == sign(val2)) && (sign(val1) != sign(res8))
Chalf = res4 > 0x0F
Cout = res > 0xFF
flags = SZ53table[res8] | (overflow ? PV : 0) | (Chalf ? H : 0) | (Cout ? C : 0)
```

### sub8(val1, val2, CIn, resOut)

Subtraction is implemented **via add8** for reuse:

```
add8(val1, (~val2) & 0xFF, !CIn, resOut)
flags = resOut[1] ^ (H | C) | N
```

This is a crucial implementation trick: `val1 - val2 - carry` is equivalent to `val1 + (~val2) + (!carry)`, then flipping H and C and setting N.

### add16(val1, val2, CIn, resOut)

Performs 16-bit addition by calling `add8` on low then high bytes, propagating carry:

```
add8(low1, low2, CIn, resL)
add8(high1, high2, resL.flags & C, resH)
res16 = (resH.byte << 8) | resL.byte
flags = S(from high) | Z(if res16==0) | 5(from high) | H(from high) | 3(from high) | PV(from high) | C(from high)
```

Note: for `ADD HL,ss` and similar, S/Z/PV are **not** updated in the real Z80; the code here computes them but masks them away later.

### sub16(val1, val2, CIn, resOut)

Same trick as sub8: `add16(val1, (~val2)&0xFFFF, !CIn, ...)` then flip H/C and set N.

### shl8(val, rightIn, resOut)

Shift left. `rightIn` is the bit to feed into bit 0. Carry = bit 7 of `val`.

```
res = ((val << 1) | rightIn) & 0xFF
flags = SZ53Ptable[res] | (Cout ? C : 0)
```

### shr8(val, leftIn, resOut)

Shift right. `leftIn` is the bit to feed into bit 7. Carry = bit 0 of `val`.

```
res = ((val >>> 1) | (leftIn << 7)) & 0xFF
flags = SZ53Ptable[res] | (Cout ? C : 0)
```

These two helpers implement:
- `RLC` / `RRC` — `rightIn/leftIn` = bit from the value itself.
- `RL` / `RR` — `rightIn/leftIn` = previous carry flag.
- `SLA` — `rightIn = 0`.
- `SRA` — `leftIn = bit 7 of val`.
- `SRL` — `leftIn = 0`.
- `SLL` — `rightIn = 1` (undocumented).

## Instruction Groups

### 1. NOP and basic control

- `NOP` (0x00): `t=4`, `m=1`. Do nothing.
- `HALT` (0x76): `t=4`, `m=1`. Set `halted = 1`.

### 2. 8-bit loads

The 8-bit LD group is the densest block of the opcode map (0x40–0x7F, excluding HALT).

```
LD r,r'       t=4, m=1         r = r'
LD r,(HL)     t=7, m=1         r = mmu.r8(HL)
LD (HL),r     t=7, m=1         mmu.w8(HL, r)
LD r,n        t=7, m=2         r = mmu.r8(PC+1)
LD (HL),n     t=10, m=2        mmu.w8(HL, mmu.r8(PC+1))
```

Where `r` is one of B, C, D, E, H, L, A.

### 3. 8-bit arithmetic

All 8-bit ALU instructions (0x80–0xBF) follow a regular pattern:

```
ADD A,r       t=4, m=1         add8(A, r, 0, res); A=res[0]; F=res[1]
ADC A,r       t=4, m=1         add8(A, r, F&C, res); A=res[0]; F=res[1]
SUB r         t=4, m=1         sub8(A, r, 0, res); A=res[0]; F=res[1]
SBC A,r       t=4, m=1         sub8(A, r, F&C, res); A=res[0]; F=res[1]
AND r         t=4, m=1         A &= r; F = SZ53Ptable[A] | H
XOR r         t=4, m=1         A ^= r; F = SZ53Ptable[A]
OR r          t=4, m=1         A |= r; F = SZ53Ptable[A]
CP r          t=4, m=1         sub8(A, r, 0, res); F = res[1] but preserve F_5/F_3 from operand r
```

Immediate versions (0xC6, 0xCE, 0xD6, 0xDE, 0xE6, 0xEE, 0xF6, 0xFE) read `n` at `PC+1` with `t=7, m=2`.

Memory versions (`(HL)` instead of `r`) use `t=7, m=1`.

**Important CP subtlety:** For `CP (HL)`, the undocumented F_5 and F_3 flags come from the **memory operand**, not from A. For `CP r`, they come from the register operand.

**INC/DEC r:**

```
INC r         t=4, m=1         add8(r, 1, 0, res); r=res[0]; F = (res[1] & ~C) | (oldF & C)
DEC r         t=4, m=1         sub8(r, 1, 0, res); r=res[0]; F = (res[1] & ~C) | (oldF & C)
```

Carry is preserved; all other flags updated.

### 4. 16-bit loads and stack

```
LD ss,nn      t=10, m=3        ss = mmu.r16(PC+1)     (ss = BC, DE, HL, SP)
LD (nn),HL    t=16, m=3        mmu.w16(mmu.r16(PC+1), HL)
LD HL,(nn)    t=16, m=3        HL = mmu.r16(mmu.r16(PC+1))
LD (nn),A     t=13, m=3        mmu.w8(mmu.r16(PC+1), A)
LD A,(nn)     t=13, m=3        A = mmu.r8(mmu.r16(PC+1))
LD SP,HL      t=6,  m=1        SP = HL
```

Stack operations:

```
PUSH ss       t=11, m=1        push16(ss)
POP ss        t=10, m=1        ss = pop16()
```

`push16` writes high byte to `SP-1`, low byte to `SP-2`, then `SP = SP-2`.
`pop16` reads low at `SP`, high at `SP+1`, then `SP = SP+2`.

### 5. Jumps, calls, returns

**Relative jumps:**

```
JR e          t=12, m=0        PC = PC + 2 + signed8(mmu.r8(PC+1))
JR NZ,e       t=12/7, m=0/2    if Z: PC+=2 (7cy, m=2); else jump (12cy, m=0)
JR Z,e        t=12/7, m=0/2    if Z: jump; else PC+=2
JR NC,e       t=12/7, m=0/2    if C: PC+=2; else jump
JR C,e        t=12/7, m=0/2    if C: jump; else PC+=2
DJNZ e        t=13/8, m=0/2    B--; if B==0: PC+=2 (8cy, m=2); else jump (13cy, m=0)
```

**Absolute jumps:**

```
JP nn         t=10, m=0        PC = mmu.r16(PC+1)
JP cc,nn      t=10, m=0/3      if condition: PC=nn (10cy, m=0); else PC+=3 (10cy, m=3)
JP (HL)       t=4,  m=0        PC = HL
JP (IX)       t=8,  m=0        PC = IX   (DD prefix)
```

**Calls and returns:**

```
CALL nn       t=17, m=0        push16(PC+3); PC=nn
CALL cc,nn    t=17/10, m=0/3   if condition: push16(PC+3); PC=nn; else PC+=3
RET           t=10, m=0        PC = pop16()
RET cc        t=11/5, m=0/1    if condition: PC=pop16(); else PC+=1
RST p         t=11, m=0        push16(PC+1); PC=p   (p = 0x00,0x08,0x10,...,0x38)
```

**Note on timing and length:** When a condition is **not** met, the instruction must still read the operand bytes to advance the PC correctly. In implementations used for testing, you may want to read these bytes without triggering "memory read" side-effects or logging, but functionally it's a 16-bit read.

### 6. Rotates, shifts, and bits (CB prefix)

After `CB`, read one more byte. All CB instructions take at least `t=8, m=2`.

**Rotate/shift registers:**

```
RLC r         t=8, m=2         shl8(r, r&0x80, res); r=res[0]; F=res[1]
RRC r         t=8, m=2         shr8(r, r&1,     res); r=res[0]; F=res[1]
RL r          t=8, m=2         shl8(r, F&C,     res); r=res[0]; F=res[1]
RR r          t=8, m=2         shr8(r, F&C,     res); r=res[0]; F=res[1]
SLA r         t=8, m=2         shl8(r, 0,       res); r=res[0]; F=res[1]
SRA r         t=8, m=2         shr8(r, r&0x80,  res); r=res[0]; F=res[1]
SRL r         t=8, m=2         shr8(r, 0,       res); r=res[0]; F=res[1]
SLL r*        t=8, m=2         shl8(r, 1,       res); r=res[0]; F=res[1]
```

For memory:

```
RLC (HL)      t=15, m=2         val=mmu.r8(HL); shl8(val, val&0x80, res); mmu.w8(HL, res[0]); F=res[1]
... etc for all 8 variants
```

**BIT n,r:**

```
BIT n,r       t=8, m=2         val = r & (1<<n)
                                 F = (val&S) | (val?0:(Z|PV)) | (r & (F_5|F_3)) | H | (oldF & C)
```

The undocumented F_5 and F_3 come from the **source register**.

**BIT n,(HL):**

```
BIT n,(HL)    t=12, m=2         val = mmu.r8(HL) & (1<<n)
                                 F = (val&S) | (val?0:(Z|PV)) | ((HL>>>8) & (F_5|F_3)) | H | (oldF & C)
```

For `(HL)`, F_5/F_3 come from the **high byte of the address**.

**RES/SET n,r and (HL):**

```
RES n,r       t=8, m=2         r &= ~(1<<n)
SET n,r       t=8, m=2         r |= (1<<n)
RES n,(HL)    t=15, m=2        mmu.w8(HL, mmu.r8(HL) & ~(1<<n))
SET n,(HL)    t=15, m=2        mmu.w8(HL, mmu.r8(HL) | (1<<n))
```

### 7. IX and IY prefix (DD / FD)

The `DD` prefix uses `IX`; the `FD` prefix uses `IY`. The implementation adds a large set of explicit prefixed opcodes to the table (e.g. `0xDD46` for `LD B,(IX+d)`).

**Displacement reads:** All `(IX+d)` instructions read a signed displacement at `PC+2` (or `PC+2` inside the prefix loop). The effective address is `IX + signed8(displ)`.

Key patterns:

```
LD r,(IX+d)         t=19, m=3         r = mmu.r8(IX + displ)
LD (IX+d),r         t=19, m=3         mmu.w8(IX + displ, r)
LD (IX+d),n         t=19, m=4         mmu.w8(IX + displ, mmu.r8(PC+3))
```

**Arithmetic with (IX+d):**

```
ADD A,(IX+d)        t=19, m=3         add8(A, mmu.r8(IX+displ), 0, res); A=res[0]; F=res[1]
SUB (IX+d)          t=19, m=3         sub8(A, mmu.r8(IX+displ), 0, res); A=res[0]; F=res[1]
AND/XOR/OR/CP (IX+d)  t=19, m=3       same patterns as base, operand from memory
```

**IX high/low halves (undocumented):**

`INC IXH`, `DEC IXH`, `LD IXH,n`, and all `LD IXH,r` variants exist. They behave like their HL counterparts but target the `IXh` / `IXl` registers. `t=8, m=2` (or `t=11, m=3` for `LD IXH,n`).

**DDCB / FDCB prefix:**

These are 4-byte instructions:

```
DD CB d opcode
```

The displacement `d` is read **before** the final CB opcode byte. The lookup key is `0xDDCBxx`.

Examples:

```
LD B,RLC (IX+d)     t=23, m=4
    addr = IX + displ
    val = mmu.r8(addr)
    shl8(val, val&0x80, res)
    B = res[0]
    mmu.w8(addr, res[0])
    F = res[1]

BIT n,(IX+d)        t=20, m=4
    addr = IX + displ
    val = mmu.r8(addr) & (1<<n)
    F = (val&S) | (val?0:(Z|PV)) | ((addr>>>8)&(F_5|F_3)) | H | (oldF&C)
```

Note: for `BIT n,(IX+d)`, the undocumented F_5/F_3 come from the **high byte of the effective address**.

### 8. ED prefix: block I/O and 16-bit arithmetic

Only a subset of ED instructions is implemented; many ED opcodes throw "not implemented".

**16-bit arithmetic:**

```
ADC HL,ss       t=15, m=2         add16(HL, ss, F&C, res); HL=res[0]; F=res[1]
SBC HL,ss       t=15, m=2         sub16(HL, ss, F&C, res); HL=res[0]; F=res[1]
```

**IN/OUT:**

```
IN r,(C)        t=12, m=2         r = port_reader(C, B); F = (oldF&C) | SZ53Ptable[r]
OUT (C),r       t=12, m=2         port_writer(C, r, B)
```

Note: the second argument to `_in` and `_out` is `B` (used as expected value in the test harness).

```
IN A,(n)        t=11, m=2         A = port_reader(n, A)   where n = mmu.r8(PC+1)
OUT (n),A       t=11, m=2         port_writer(n, A, A)
```

**LD instructions:**

```
LD A,I          t=8,  m=2         A = I; F = (oldF&C) | SZ53Ptable[A] | (IFF2?PV:0)
LD I,A          t=8,  m=2         I = A
LD A,R          t=8,  m=2         A = R; F = (oldF&C) | SZ53Ptable[A] | (IFF2?PV:0)
LD R,A          t=8,  m=2         R = A
LD dd,(nn)      t=20, m=4         dd = mmu.r16(mmu.r16(PC+2))   (dd = BC,DE,HL,SP)
LD (nn),dd      t=20, m=4         mmu.w16(mmu.r16(PC+2), dd)
```

**Block instructions:**

All block instructions update flags in a specific way. The general pattern is:

```
LDI             t=16, m=2
    mmu.w8(DE, mmu.r8(HL))
    DE++; HL++; BC--
    F = (oldF & (S|Z|C)) | (BC?0:PV) | N_cleared

LDIR            t=16/21, m=2
    same as LDI, but if BC != 0: PC -= 2 (repeat), t=21 for the repeating iteration

LDD / LDDR      similar, but DE-- and HL--

CPI             t=16, m=2
    val = mmu.r8(HL); HL++; BC--
    sub8(A, val, 0, res)
    F = res[1] with special H handling | (BC?0:PV) | N_set
    If H set: F_3 = (A - val - H) bit 3; F_5 = bit 1

CPIR / CPD / CPDR  similar with repeat/DEcrement

INI / IND / OUTI / OUTD / INIR / INDR / OTIR / OTDR
    read/write port, then increment/decrement HL and B, set flags
```

**NEG:**

```
NEG             t=8, m=2         sub8(0, A, 0, res); A=res[0]; F=res[1]
```

### 9. Interrupts and HALT

**HALT:** Advances `PC` past the HALT opcode and sets `halted = 1`. While halted, `step()` consumes 4 cycles without executing another instruction. An accepted interrupt clears `halted` and pushes the post-HALT `PC`, so returning from the interrupt continues after HALT.

**Interrupt model:**

Only **IM 1** is implemented.

```
irq():
    if IFF1:
        halted = 0
        IFF1 = 0
        IFF2 = 0
        push16(PC)
        PC = 0x0038
        return 13 cycles   (RST 38 + 2 wait states)
    else:
        return 0
```

`EI` and `DI` instructions (in the base opcode map) set/clear `IFF1` and `IFF2`.

`IM 0`, `IM 2`, and `NMI` are not implemented in this codebase.

##### Interrupt timing

*by Achim Flammenkamp*

Only at the end of an instruction execution, except a NOP in case HALT, a LDD in case LDDR, a OUTI in case OTIR, etc., the CPU checks for an interrupt request. Thus the INT-pin should be active for at least 23 clock ticks because some IX resp. IY instruction last so long. Now an interrupt is accepted if INT-pin is low(active) and the interrupt flip flop IFF1 is set or the NMI-pin is respectively was active during the just performed instruction. If this is the case, the following happens:  
Immediately IFF1 is reset to 0 and if INT-pin is low also IFF2 is reset to 0. Then the behavior depends whether it is a non maskable interrupt (NMI) or a maskable interrupt (INT). In the later case the interrupt mode (IM) of the CPU is also decisive:

-   NMI  
    It takes 11 clock cycles to get to #0066:
    1.  M1 cycle: 5 T states to do an opcode read and decrement SP
    2.  M2 cycle: 3 T states write high byte of PC to the stack and decrement SP
    3.  M3 cycle: 3 T states write the low byte of PC and jump to #0066.
-   INT and interrupt mode 0 set  
    In this mode, timing depends on the instruction put on the bus. The interrupt processing last 2 clock cycles more than this instruction usually needs.  
    Two typical examples follow:  
    
    a RST n on the data bus, it takes 13 cycles to get to 'n':1.  M1 cycle: 7 ticks  
        acknowledge interrupt and decrement SP
    2.  M2 cycle: 3 ticks  
        write high byte and decrement SP
    3.  M3 cycle: 3 ticks  
        write low byte and jump to 'n'
    
    With a CALL nnnn on the data bus, it takes 19 cycles:1.  M1 cycle: 7 ticks  
        acknowledge interrupt
    2.  M2 cycle: 3 ticks  
        read low byte of 'nnnn' from data bus
    3.  M3 cycle: 3 ticks  
        read high byte of 'nnnn' and decrement SP
    4.  M4 cycle: 3 ticks  
        write high byte of PC to the stack and decrement SP
    5.  M5 cycle: 3 ticks  
        write low byte of PC and jump to 'nnnn'.
-   INT and interrupt mode 1 set  
    It takes 13 clock cycles to reach #0038:
    1.  M1 cycle: 7 ticks  
        acknowledge interrupt and decrement SP
    2.  M2 cycle: 3 ticks  
        write high byte of PC onto the stack and decrement SP
    3.  M3 cycle: 3 ticks  
        write low byte onto the stack and to set PC to #0038.
-   INT and interrupt mode 2 set  
    It takes 19 clock cycles to get to the interrupt routine:
    1.  M1 cycle: 7 ticks  
        acknowledge interrupt and decrement SP
    2.  M2 cycle: 3 ticks  
        write high byte of PC onto stack and decrement SP
    3.  M3 cycle: 3 ticks  
        write low byte onto the stack
    4.  M4 cycle: 3 ticks  
        read low byte from the interrupt vector
    5.  M5 cycle: 3 ticks  
        read high byte from bus and jump to interrupt routine

Some remarks:

1.  "acknowledge interrupt" means pin IORQ gets together with M1-pin active/low. Furthermore the CPU adds 2 wait states to the normal machine cycle.
2.  Quoted remark*:
    
    -   If a LD A,I or LD A,R (which copy IFF2 to the P/V flag) is interrupted, then the P/V flag is reset, even if interrupts were enabled beforehand.
    -   If interrupts are disabled when a EI instruction is interrupted, then the interrupt will not occur until after the instruction following the EI, as when IFF1 is sampled during the one and only machine-cycle of the EI, it will be reset.
    
    *
3.  An INT will let the INT-pin low(active) until it is indirectly reseted by an RETI or other external hardware. In contrast a signal at the NMI-pin will be recognized when its state going from high to low! Thus it is not a level trigger signal, but a pulse which is stored internally by the CPU until the next M1 cycle.

#### Reset Timing

One can consider a reset (RESET-pin gets low) as a very special interrupt. If this occurs, the following happens in one machine cycle.

It takes 3 clock cycles:
-   IFF1 and IFF2 as well as interrupt mode are set to 0.
-   PC is set to 0, and the I and R registers are reset.
-   Other CPU registers are not hardware-defined by reset.

### 10. Misc: DAA, EX, EXX, CPL, SCF, CCF

**DAA (0x27):**

```
carry = F & C
lownibble = A & 0x0F
add = 0
if (F&H) or (lownibble > 9): add = 6
if carry or (A > 0x99): add |= 0x60; carry = C
if F&N: sub8(A, add, 0, res)
else:    add8(A, add, 0, res)
A = res[0]
F = (oldF & N) | SZ53Ptable[A] | (res[1] & H) | carry
```

**CPL (0x2F):**

```
A = ~A & 0xFF
F = (oldF & (S|Z|PV|C)) | H | N | (A & (F_5|F_3))
```

**SCF (0x37):**

```
F = (oldF & (S|Z|PV)) | (A & (F_5|F_3)) | C
```

**CCF (0x3F):**

```
F = (oldF & (S|Z|PV)) | (A & (F_5|F_3)) | ((oldF&C)<<4) | ((oldF&C) ^ C)
```
The old carry is copied into H, then inverted for C.

**EX AF,AF' (0x08):** Swap A and A', F and F'.

**EXX (0xD9):** Swap BC, DE, HL with their shadow counterparts.

**EX DE,HL (0xEB):** Swap DE and HL.

**EX (SP),HL (0xE3):**

```
t=19, m=1
val = mmu.r16(SP)
mmu.w16reverse(SP, HL)   // writes HL in reverse order to match Z16 spec
HL = val
```

**EX (SP),IX / EX (SP),IY** (DD/FD prefixed): same but with IX/IY, `t=23, m=2`.

## Testing

When building a Z80 emulator, two standard test suites are highly recommended:

- **FUSE tests**: A set of `.in` and `.expected` files. Each test case provides an initial register state and a block of memory, runs exactly one instruction, and provides the expected final register state and memory changes. Your emulator should have a harness to parse these, load the state, call `step()`, and assert equality with the expected output.
- **ZEXDOC / ZEXALL**: These are actual Z80 programs that run on the emulator itself. They exercise the CPU with millions of combinations and output pass/fail text via a mocked BDOS call (usually intercepting `CALL 5` or `OUT` instructions to print characters). `ZEXDOC` checks documented flags, while `ZEXALL` checks undocumented flags.

A robust test harness will typically use a "Fake MMU" that tracks memory/port accesses for comparison against FUSE test logs.

## Step-by-Step Implementation Plan

To build a working Z80 from scratch based on this design, proceed in this order:

### Step 0: Register file and reset
- Create the memory layout for registers (either via unions/overlays or independent variables with getters/setters).
- If using an overlay/union, verify little-endian mapping: writing `0x1234` to a 16-bit view should make the high byte `0x12` and low byte `0x34`.
- Implement `reset()` with the values listed above.

### Step 1: NOP only
- Implement `step()` with the fetch/decode/execute loop.
- Handle only opcode `0x00` (NOP). For everything else, throw "not implemented".
- Set `cycles = 4`, `length = 1` for NOP.
- Ensure `PC` advances correctly.
- Verify with a tiny test that executing one instruction increments PC by 1.

### Step 2: 8-bit loads and simple 16-bit loads
- Add `LD r,r'`, `LD r,n`, `LD r,(HL)`, `LD (HL),r`, `LD (HL),n`.
- Add `LD ss,nn` for BC, DE, HL, SP.
- Add `LD (nn),HL` and `LD HL,(nn)`.
- These cover the most common data movement instructions.

### Step 3: Stack operations
- Implement `push16` / `pop16`.
- Add `PUSH ss` and `POP ss`.
- Verify stack pointer behavior with simple tests.

### Step 4: Jumps (relative and absolute)
- Add `JR e` (unconditional).
- Add conditional `JR cc,e` (NZ, Z, NC, C).
- Add `JP nn` and `JP cc,nn`.
- Add `JP (HL)`.
- Test that branching changes PC correctly and that un-taken branches advance past the operand bytes.

### Step 5: Calls and returns
- Add `CALL nn`, `CALL cc,nn`.
- Add `RET`, `RET cc`.
- Add `RST p`.
- Add `DJNZ e`.
- Test with small subroutines.

### Step 6: 8-bit arithmetic (ADD/SUB/ADC/SBC/AND/XOR/OR/CP)
- Implement the `add8` and `sub8` helpers first.
- Add all register and immediate forms.
- Add `INC r`, `DEC r`, `INC (HL)`, `DEC (HL)`.
- Add `ADD A,(HL)`, `SUB (HL)`, etc.
- Use the FUSE `tests.in` data to verify flag behavior.

### Step 7: Rotates and shifts (CB prefix)
- Implement `shl8` and `shr8`.
- Add the CB dispatch logic: after `CB`, read the next byte and look up in the CB table.
- Implement `RLC`, `RRC`, `RL`, `RR`, `SLA`, `SRA`, `SRL` for registers and `(HL)`.
- Implement `BIT`, `RES`, `SET`.
- The FUSE tests are very strict here about undocumented flags.

### Step 8: IX and IY (DD / FD prefix)
- Extend the prefix decoder to handle DD and FD.
- Add the "fall through to base opcode" behavior for undefined prefixed opcodes.
- Implement `LD IX,nn`, `LD (IX+d),n`, `LD r,(IX+d)`, `LD (IX+d),r`.
- Implement `ADD A,(IX+d)`, `SUB (IX+d)`, etc.
- Implement `INC (IX+d)`, `DEC (IX+d)`.
- Implement `JP (IX)`.

### Step 9: DDCB / FDCB prefix
- Extend the decoder for the 4-byte `DD CB d opcode` form.
- Read displacement before the final CB opcode.
- Implement `LD r,ROT (IX+d)` and `ROT (IX+d)`.
- Implement `BIT n,(IX+d)` with the correct undocumented flag source (high byte of effective address).
- Implement `RES n,(IX+d)` and `SET n,(IX+d)`.

### Step 10: ED prefix (16-bit arithmetic, IN/OUT, block ops)
- Implement `SBC HL,ss`, `ADC HL,ss`.
- Implement `LD dd,(nn)`, `LD (nn),dd`.
- Implement `IN r,(C)`, `OUT (C),r`, `IN A,(n)`, `OUT (n),A`.
- Implement `LD A,I`, `LD I,A`, `LD A,R`, `LD R,A`.
- Implement `NEG`.
- Implement block instructions: `LDI`, `LDIR`, `LDD`, `LDDR`, `CPI`, `CPIR`, `CPD`, `CPDR`.
- Implement `INI`, `IND`, `OUTI`, `OUTD` and their repeating forms.

### Step 11: Interrupts and HALT
- Implement `HALT`.
- Implement `EI`, `DI`, `IM 0`, `IM 1`, `IM 2`.
- Implement `irq()` for IM 1 (RST 0x38).
- Implement `RETI` and `RETN` if needed (the code has `retn()` which restores `IFF1 = IFF2`).

### Step 12: DAA, EX, EXX, misc
- Implement `DAA`. This is tricky; use the algorithm described above.
- Implement `EX AF,AF'`, `EXX`, `EX DE,HL`, `EX (SP),HL`.
- Implement `CPL`, `SCF`, `CCF`.

### Step 13: Polish and testing
- Run FUSE tests after each step to ensure correctness.
- Use ZEXDOC/ZEXALL to catch edge cases.
- Ensure the `R` register updates match the number of opcode bytes fetched.
- Verify that reads in conditional jumps do not affect observable state.

## Key Design Notes for Implementers

1. **Little-endian considerations:** If using memory overlays/unions to pair 8-bit registers, be aware of the host system's endianness. On big-endian hosts, you must manually pair registers or reverse the struct fields.
2. **Subtraction via addition:** `sub8` and `sub16` are easily implemented by inverting the subtrahend and using the `add` helper. This reduces code duplication but means you must carefully flip `H`, `C`, and set `N` afterward.
3. **Conditional read semantics:** When a conditional jump/call/ret is **not** taken, the operand bytes must still be consumed. A common approach is setting the instruction `length` to the full length in the "not taken" branch to ensure `PC` advances.
4. **Prefix handling:** Multiple `DD`/`FD` prefixes stack as NOPs. The instruction fetch loop should consume them until a non-prefix byte appears. Only the last prefix matters.
5. **Undocumented flags:**
   - F_5 and F_3 usually copy bits 5 and 3 of the **result**.
   - For `CP r`, they copy from the **operand register**.
   - For `BIT n,(HL)` and `BIT n,(IX+d)`, they copy from the **high byte of the address**.
   - Handling these precisely is critical for passing ZEXALL and FUSE tests.
6. **Disassembly coupling:** If your emulator supports disassembly, you may want your opcode handlers to save operands (like `n`, `nn`, or `d`) into state variables so an external module can easily disassemble the last executed instruction.
