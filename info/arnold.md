# Arnold Technical Reference

Amstrad CPC 464 hardware information for emulator authors and low-level
software developers.

"Arnold" was Amstrad's internal codename for the CPC 464 project. In rtvc the
machine is called `Cpc`. It is an experimental game-conversion aid, not a
complete CPC emulator.

Most of this document describes the machine without reference to any
implementation: memory, I/O decoding, Gate Array, CRTC, interrupts, video,
keyboard, sound, cassette, and firmware conventions. Short notes mark where
rtvc departs from the hardware. [rtvc.md](rtvc.md) holds the full
implementation description.

## Technical Data

| --- | --- |
| CPU | Zilog Z80A |
| CPU clock | 4,000,000 Hz, derived from a 16 MHz master clock |
| Effective speed | memory accesses aligned to 1 µs slots, roughly 3.3 MHz in practice |
| CPU address space | 64 KiB, with lower and upper ROM overlays |
| RAM | 64 KiB |
| ROM | 16 KiB OS (lower), 16 KiB BASIC 1.0 (upper) |
| Video RAM | 16 KiB of main RAM, normally `&C000-&FFFF` |
| Video controller | 6845 CRTC (several types fitted; see [CRTC](#crtc)) |
| Custom logic | Amstrad 40007/40010 Gate Array |
| Video modes | 160 x 200 x 16, 320 x 200 x 4, 640 x 200 x 2 (default geometry) |

## Clock and Frame Timing

The Gate Array divides a 16 MHz master clock into:

```text
CPU clock         4 MHz
CRTC clock        1 MHz   (one character = 1 µs = 4 CPU T-states)
AY clock          1 MHz
pixel clock       16 MHz (mode 2), 8 MHz (mode 1), 4 MHz (mode 0)
```

The firmware's default CRTC programming produces:

```text
line              64 characters = 64 µs = 256 T-states
frame             39 character rows x 8 raster lines = 312 lines
frame budget      312 x 256 = 79,872 T-states
frame rate        1,000,000 / 19,968 = approximately 50.08 Hz
```

Software can reprogram the CRTC freely, so an emulator must derive timing
from CRTC state and not assume the default frame.

### Wait states

The Gate Array and the CRTC share RAM with the CPU. Each 1 µs slot gives the
video circuit its two-byte fetch, and the Gate Array holds `/WAIT` so that CPU
memory and I/O accesses line up with the slot boundaries. The visible result
is that instruction times are effectively rounded up to whole microseconds.
CPC programmers count instruction times in "NOPs" (1 µs units) instead of
T-states:

| Instruction | Z80 T-states | CPC time |
| --- | ---: | ---: |
| `NOP` | 4 | 1 µs |
| `LD A,(HL)` | 7 | 2 µs |
| `LD (HL),n` | 10 | 3 µs |
| `PUSH HL` | 11 | 4 µs |
| `OUT (C),r` | 12 | 4 µs |
| `LDI` | 16 | 5 µs |

The exact rule depends on where each M-cycle's memory or I/O access falls
inside the instruction, so some instructions round differently from a simple
"round the total up to 4 T-states" rule (`LDI` is one: 16 T-states, but
5 µs). Cycle-exact raster effects need the per-instruction CPC timing table.

## Reset State

At reset:

- the Z80 starts at `PC=&0000` with interrupts disabled;
- the Gate Array enables both the lower and the upper ROM;
- the Gate Array interrupt counter is cleared;
- the 8255 sets all three ports to input (control word `&9B`);
- the AY registers are cleared;
- CRTC registers are undefined until the firmware programs them;
- RAM contents are not guaranteed.

The firmware selects mode 1, programs the CRTC for the 50 Hz 40 x 25
display with the screen at `&C000`, sets the default inks, and enters
BASIC 1.0.

## CPU and Bus Conventions

### Z80 use

The CPC does not modify the Z80 instruction set. Interrupt modes, `HALT`,
and refresh behave normally, apart from the slot alignment described above.
The Gate Array does not drive the data bus during interrupt acknowledge, so
interrupt mode 2 vectors read an undefined value (usually `&FF`). Software
uses interrupt mode 1.

### Port decoding

CPC peripherals decode individual bits of the I/O address high byte. The low
byte is ignored by the internal hardware. Ports are therefore addressed with
`OUT (C),r` and `IN r,(C)`, with the device selected by B:

```text
LD BC,&7F10   ; Gate Array
OUT (C),C
```

`OUT (n),A` places A on the high byte. It works only when A itself selects
the intended device.

Because each device watches only its own address bit, an address with
several of those bits low selects several devices at once. Software normally
avoids this.

### Byte order

The Z80 is little-endian.

## Memory Map

The 464 has 64 KiB of RAM and two 16 KiB ROMs overlaid on it:

| CPU range | Read when ROM enabled | Read when ROM disabled | Writes |
| --- | --- | --- | --- |
| `&0000-&3FFF` | lower ROM (OS firmware) | RAM | RAM |
| `&4000-&7FFF` | RAM | RAM | RAM |
| `&8000-&BFFF` | RAM | RAM | RAM |
| `&C000-&FFFF` | upper ROM (BASIC 1.0) | RAM | RAM |

Writes always reach RAM, including under an enabled ROM. Video fetches
always read RAM, so the default screen at `&C000-&FFFF` lies under BASIC and
remains displayed while BASIC is mapped.

The 464 has no RAM banking; the Gate Array RAM-configuration command exists
only with the 6128 or a RAM expansion.

### Firmware RAM use

With BASIC running, the firmware and BASIC reserve the top of RAM below the
screen, from about `&AB80` to `&BFFF` on the 464 (BASIC 1.0 reports
`HIMEM` = 43903 = `&AB7F`). This includes the main jumpblock at `&BB00`, the
machine stack below `&C000`, and firmware variables. The bottom of RAM holds
the RST vector copies (`&0000-&003F`) and BASIC's program area from `&0170`.

A game that takes over the machine can use all 64 KiB. It must then provide
its own interrupt handler at `&0038` in RAM and keep the lower ROM disabled.

## Gate Array

The Gate Array is write-only. Bits 7-6 of the data byte select the command:

| Bits 7-6 | Command | Data |
| --- | --- | --- |
| `00` | select pen | bit 4 = 1 selects the border; otherwise bits 3-0 = pen 0-15 |
| `01` | set colour | bits 4-0 = hardware colour for the selected pen |
| `10` | mode and ROM configuration | see below |
| `11` | RAM configuration | 6128 or RAM expansion only |

Mode and ROM configuration byte:

```text
bit 7-6  10
bit 5    unused
bit 4    1 = reset the interrupt counter and clear a pending interrupt
bit 3    1 = disable upper ROM
bit 2    1 = disable lower ROM
bit 1-0  screen mode for the next line
```

A mode change takes effect at the next HSYNC, so a mode can differ from line
to line but not within a line. ROM enables take effect immediately.

The firmware leaves the selected pen and ROM state in its own variables.
Software that pokes the Gate Array directly and then calls the firmware must
restore what the firmware expects.

and 26 is bright white (hardware 11). Disassembled games almost always write
hardware numbers. BASIC listings and firmware calls use firmware numbers.

## CRTC

The CRTC generates memory addresses, raster addresses, display enable, and
sync. Generic 6845 register behavior is not repeated here.

### Firmware default programming

| Register | Value | Meaning |
| --- | ---: | --- |
| R0 | 63 | horizontal total: 64 characters per line |
| R1 | 40 | horizontal displayed: 40 characters = 80 bytes |
| R2 | 46 | HSYNC position |
| R3 | `&8E` | HSYNC width 14, VSYNC width 8 lines (type 0 and 3) |
| R4 | 38 | vertical total: 39 character rows |
| R5 | 0 | vertical total adjust |
| R6 | 25 | vertical displayed: 25 rows |
| R7 | 30 | VSYNC position |
| R8 | 0 | non-interlaced |
| R9 | 7 | 8 raster lines per row |
| R12/R13 | `&30`/`&00` | display start: screen at `&C000`, offset 0 |

### CRTC types

CPC 464s were built with several CRTC chips that differ in edge cases. CPC
literature numbers them:

| Type | Chip | Notable differences |
| --- | --- | --- |
| 0 | Hitachi HD6845S / UMC UM6845 | R3 bits 7-4 set VSYNC width (0 = 16); HSYNC width 0 gives no HSYNC |
| 1 | UMC UM6845R | VSYNC fixed at 16 lines; status register at `&BExx`; R12/R13 changes act mid-frame |
| 2 | Motorola MC6845 | VSYNC fixed at 16 lines; HSYNC width 0 = 16 |
| 3, 4 | Amstrad ASIC emulations | later machines (Plus range, late 6128s), not original 464s |

Ordinary games program only the firmware-like registers and work on all
types. Demos and some late games detect the type and use type-specific
tricks such as mid-frame R12/R13 changes for split screens.

## Interrupt System

The Gate Array counts HSYNC pulses with a 6-bit counter:

1. At the end of each HSYNC the counter increments.
2. When it reaches 52, it resets to 0 and the Gate Array raises `/INT`.
3. Two HSYNCs after VSYNC starts, the counter is reset to 0. If it was 32 or
   more at that moment, an interrupt is also raised.
4. `/INT` stays asserted until the Z80 acknowledges it. The acknowledge
   clears bit 5 of the counter, so the next interrupt cannot follow within
   32 lines.
5. Gate Array mode command bit 4 resets the counter and clears a pending
   interrupt.

With a 312-line frame this gives six interrupts per frame (300 Hz), one of
them locked two lines into VSYNC. Software that needs the frame position
tests VSYNC on PPI port B bit 0, or counts interrupts from the one that
arrives during VSYNC.

Interrupts are not lost when they are disabled: the request stays pending
until `EI` allows it to be acknowledged.

The firmware handler at `&0038` runs the keyboard scan, sound queue, and
ticker/frame-flyback events. Games that keep the firmware enabled must leave
time for it. Games that take over replace the `&0038` code in RAM with the
lower ROM disabled.

## Video System

### Screen modes

| Mode | Resolution (default) | Pens | Pixels per byte |
| --- | --- | ---: | ---: |
| 0 | 160 x 200 | 16 | 2 |
| 1 | 320 x 200 | 4 | 4 |
| 2 | 640 x 200 | 2 | 8 |
| 3 | 160 x 200 (undocumented) | 4 | 2 |

Every mode fetches the same number of bytes per line. Only the pixel
grouping changes, so all modes use the same screen memory layout.

### Pixel encoding

Mode 2 shows bit 7 first, one bit per pixel.

Mode 1 splits each pixel's two pen bits between the nibbles:

```text
pixel 0 = (bit3 << 1) | bit7
pixel 1 = (bit2 << 1) | bit6
pixel 2 = (bit1 << 1) | bit5
pixel 3 = (bit0 << 1) | bit4
```

Mode 0 interleaves each pixel's four pen bits:

```text
left  pen = bit1 bit5 bit3 bit7    (pen bits 3, 2, 1, 0)
right pen = bit0 bit4 bit2 bit6
```

That is, for the left pixel, pen bit 0 is byte bit 7, pen bit 1 is byte
bit 3, pen bit 2 is byte bit 5, and pen bit 3 is byte bit 1. The right pixel
uses the next lower bit in each position.

Mode 3 uses mode 0 pixel timing with only pen bits 0 and 1, so only pens
0-3 are shown.

### Screen addressing

The CRTC character clock is 1 MHz and the Gate Array fetches two bytes per
character. The video address combines the CRTC memory address (MA) and
raster address (RA):

```text
address bit  15   14   13  12  11   10 ... 1    0
source       MA13 MA12 RA2 RA1 RA0  MA9 ... MA0 byte (0/1)
```

MA13-12 choose the 16 KiB bank, RA selects one of eight 2 KiB blocks, and
MA9-0 select a 2-byte word in the block. MA11-10 are not used for the
address.

With the default R12/R13 = `&3000` and 80-byte lines, pixel row `y` in
`0..199` starts at:

```text
line address = &C000 + (y >> 3) * 80 + (y & 7) * &800
```

Consecutive raster lines within a character row are `&800` apart; the next
character row starts 80 bytes later. 25 rows use 2,000 of each 2,048-byte
block, leaving 48 unused bytes at the end of each block (`&C7D0-&C7FF`,
`&CFD0-&CFFF`, ...). Some software stores data there.

### Hardware scrolling

Changing R12/R13 moves the start of the display by whole characters (2
bytes). Because MA9-0 wrap within the 2 KiB block, the picture wraps around
inside the same 16 KiB bank. Scrolling games redraw only the newly exposed
edge and update the start address once per frame. A software line-address
calculation must then add the start offset modulo `&800` within each block.

### Overscan and splits

R1, R2, R6, and R7 can make the displayed area wider and taller than 40 x 25,
up to about 48 x 35 characters visible on a typical monitor. Wider screens
need more than 16 KiB, which is reached by letting MA cross into the next
bank. Rasters, palette changes, and mode changes can be timed to any line,
and R12/R13 can be changed between CRTC frames ("rupture") to show several
independent screen areas.

### Border

The border pen (Gate Array pen 16) fills every position where CRTC display
enable is low. Changing it with exact timing produces raster bars.

## 8255 PPI

| Port | Direction (firmware) | Function |
| --- | --- | --- |
| A (`&F4xx`) | in or out | AY data bus |
| B (`&F5xx`) | in | status inputs |
| C (`&F6xx`) | out | keyboard row, cassette, AY bus control |
| control (`&F7xx`) | write | mode set (bit 7 = 1) or port C bit set/reset (bit 7 = 0) |

The firmware normally uses control word `&82` (A out, B in, C out) and
switches to `&92` (A in) to read the AY. Writing a mode-set control word
clears the output latches.

### Port B inputs

```text
bit 7    cassette data in
bit 6    printer busy
bit 5    /EXP (expansion present)
bit 4    1 = 50 Hz, 0 = 60 Hz (factory link)
bit 3-1  distributor name link (7 = Amstrad)
bit 0    CRTC VSYNC
```

The firmware shows the distributor name in its boot banner, so the bit 3-1
link changes the startup message.

### Port C outputs

```text
bit 7-6  AY control: 00 inactive, 01 read, 10 write, 11 latch register
bit 5    cassette data out
bit 4    cassette motor relay
bit 3-0  keyboard row select (10-15 select no row)
```

## Keyboard

The keyboard and the two joystick ports form a 10 x 8 matrix. Port C bits
3-0 select a row through a decoder, and the AY's I/O port A (register 14)
reads the selected row. A pressed key reads as zero.

| Row | Bit 0 | Bit 1 | Bit 2 | Bit 3 | Bit 4 | Bit 5 | Bit 6 | Bit 7 |
| ---: | --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | Cursor Up | Cursor Right | Cursor Down | f9 | f6 | f3 | Enter (keypad) | f. |
| 1 | Cursor Left | COPY | f7 | f8 | f5 | f1 | f2 | f0 |
| 2 | CLR | `[` `{` | RETURN | `]` `}` | f4 | SHIFT | `\` `` ` `` | CONTROL |
| 3 | `^` `£` | `-` `=` | `@` `\|` | P | `;` `+` | `:` `*` | `/` `?` | `.` `>` |
| 4 | `0` `_` | `9` `)` | O | I | L | K | M | `,` `<` |
| 5 | `8` `(` | `7` `'` | U | Y | H | J | N | SPACE |
| 6 | `6` `&` | `5` `%` | R | T | G | F | B | V |
| 7 | `4` `$` | `3` `#` | E | W | S | D | C | X |
| 8 | `1` `!` | `2` `"` | ESC | Q | TAB | A | CAPS LOCK | Z |
| 9 | Joy Up | Joy Down | Joy Left | Joy Right | Fire 2 | Fire 1 | (Fire 3) | DEL |

Joystick 0 occupies row 9. A second joystick shares row 6 through the
joystick port's common line.

Without diode isolation the matrix ghosts: three keys pressed at the corners
of a rectangle make the fourth corner read as pressed.

### Reading a row directly

```text
LD BC,&F40E : OUT (C),C     ; AY register 14 on port A
LD BC,&F6C0 : OUT (C),C     ; latch register
LD BC,&F600 : OUT (C),C     ; inactive
LD BC,&F792 : OUT (C),C     ; port A input
LD BC,&F640+row : OUT (C),C ; select row, AY read
LD B,&F4 : IN A,(C)         ; row bits
LD BC,&F782 : OUT (C),C     ; port A output again
LD BC,&F600 : OUT (C),C
```

## Sound

The AY-3-8912 is the 8910 with one I/O port. On the CPC it runs at 1 MHz
and is reached only through the PPI: port A carries data, port C bits 7-6
drive BDIR/BC1.

| Register | Function |
| ---: | --- |
| 0-1 | channel A tone period (12 bits) |
| 2-3 | channel B tone period |
| 4-5 | channel C tone period |
| 6 | noise period (5 bits) |
| 7 | mixer: bits 0-2 tone off A-C, bits 3-5 noise off A-C, bit 6 port A direction |
| 8-10 | channel A-C amplitude (bits 0-3), bit 4 = envelope |
| 11-12 | envelope period (16 bits) |
| 13 | envelope shape |
| 14 | I/O port A (keyboard input) |
| 15 | I/O port B (not present on the 8912) |

```text
tone frequency      = 1,000,000 / (16 * period)  = 62,500 / period Hz
noise frequency     = 62,500 / period Hz
envelope step rate  = 1,000,000 / (256 * period) Hz
```

Register 7 bit 6 must stay 0 (port A input) or the keyboard cannot be read.

Writing a register by hand:

```text
OUT &F4xx, register
OUT &F6xx, &C0      ; latch register
OUT &F6xx, &00
OUT &F4xx, value
OUT &F6xx, &80      ; write
OUT &F6xx, &00
```

The firmware entry `MC SOUND REGISTER` (`&BD34`, A = register, C = value)
does the same. Games commonly run their music player from the 300 Hz
interrupt, or once per frame on the VSYNC interrupt.

The 464's built-in speaker is mono; the stereo socket outputs channel A left,
B centre, and C right.

## Cassette Interface

| Signal | Location |
| --- | --- |
| data in | PPI port B bit 7 |
| data out | PPI port C bit 5 |
| motor relay | PPI port C bit 4 |

Loaders measure the time between input transitions. The motor relay starts
and stops the built-in recorder, so the firmware and custom loaders pause
the tape between blocks by switching it off.

## Firmware Conventions

### Restart vectors

The firmware uses the Z80 RST instructions as calls that switch ROMs:

| RST | Address | Name | Purpose |
| --- | --- | --- | --- |
| 0 | `&0000` | RESET ENTRY | cold start |
| 1 | `&0008` | LOW JUMP | jump into the lower ROM with a ROM state |
| 2 | `&0010` | SIDE CALL | call a sibling expansion ROM |
| 3 | `&0018` | FAR CALL | call any ROM address with a ROM state |
| 4 | `&0020` | RAM LAM | `LD A,(HL)` from RAM regardless of ROMs |
| 5 | `&0028` | FIRM JUMP | jump into the lower ROM |
| 6 | `&0030` | user restart | free for programs |
| 7 | `&0038` | interrupt entry | IM 1 handler |

Copies of these entries live in RAM at the same addresses, so they still work
when the lower ROM is disabled.

### Main jumpblock

The jumpblock from `&BB00` holds three-byte entries, mostly `RST 1` low
jumps, grouped by firmware pack (KM keyboard, TXT text, GRA graphics,
SCR screen, CAS cassette, SOUND, KL kernel, MC machine). Some entries
disassembled games commonly call:

| Address | Entry | Purpose |
| --- | --- | --- |
| `&BB06` | KM WAIT CHAR | wait for a character |
| `&BB18` | KM WAIT KEY | wait for a key |
| `&BB1B` | KM READ KEY | read a key without waiting |
| `&BB1E` | KM TEST KEY | test one key number |
| `&BB5A` | TXT OUTPUT | print a character |
| `&BC0E` | SCR SET MODE | set mode and clear the screen |
| `&BC32` | SCR SET INK | set a pen's colours |
| `&BC38` | SCR SET BORDER | set the border colours |
| `&BC77` | CAS IN OPEN | open a cassette file |
| `&BC83` | CAS IN DIRECT | load a whole file to memory |
| `&BCAA` | SOUND QUEUE | queue a sound |
| `&BD19` | MC WAIT FLYBACK | wait for VSYNC |
| `&BD34` | MC SOUND REGISTER | write an AY register |

Programs can patch jumpblock entries to intercept firmware calls. That is
also a convenient debugger hook when tracing a game's use of the firmware.
Confirm entry numbers against the firmware manual before relying on less
common ones.

## Firmware Tape Format

The firmware records a file as a series of blocks of up to 2 KiB. Each block
is written as two records, a header and the data:

1. a leader of about 2,048 one bits, which the loader uses to calibrate
   the speed;
2. a zero bit;
3. a sync byte: `&2C` for a header record, `&16` for a data record;
4. the record in 256-byte segments, each followed by a 16-bit CRC (CCITT,
   stored inverted, high byte first);
5. a trailer of 32 one bits.

Each bit is one full cycle of a square wave; a one bit is twice as long as a
zero bit. `SPEED WRITE 0` and `SPEED WRITE 1` select nominal 1000 and 2000
baud; because of the calibration leader, the loader adapts to the recorded
speed.

The 64-byte header record holds:

| Offset | Size | Meaning |
| ---: | ---: | --- |
| 0 | 16 | filename, padded with zero bytes |
| 16 | 1 | block number, from 1 |
| 17 | 1 | non-zero for the last block |
| 18 | 1 | file type: bit 0 protected; bits 3-1: 0 BASIC, 1 binary, 2 screen, 3 ASCII |
| 19 | 2 | length of this block's data |
| 21 | 2 | load address of this block |
| 23 | 1 | non-zero for the first block |
| 24 | 2 | total file length |
| 26 | 2 | entry (execution) address |
| 28 | 36 | unused by the firmware |

Many commercial games load only a short firmware-format loader and then use
their own turbo or protected format.

## CDT Files

`.cdt` files use the TZX container unchanged. Firmware-format blocks are
usually stored as TZX turbo-speed data (block `&11`) with the recorded pulse
lengths; custom formats use pure tone, pulse sequence, pure data, or direct
recording blocks. TZX timings are in 3.5 MHz Spectrum T-states and must be
rescaled to the CPC's 4 MHz clock.

## System ROM Placement

The 464 needs two 16 KiB ROM images:

| ROM | Size | CPU address when enabled |
| --- | ---: | --- |
| OS firmware (lower ROM) | 16 KiB | `&0000-&3FFF` |
| BASIC 1.0 (upper ROM 0) | 16 KiB | `&C000-&FFFF` |

rtvc reads them from [roms/CPC_OS_464.ROM](../roms/CPC_OS_464.ROM) and
[roms/CPC_BASIC_1.0.ROM](../roms/CPC_BASIC_1.0.ROM).

## Comparison with the TVC

Both machines are 50 Hz Z80 computers with a 6845 CRTC and a bitmap screen,
so much of their video model lines up:

| Topic | CPC 464 | TVC |
| --- | --- | --- |
| CPU clock | 4 MHz, 1 µs slot alignment | 3.125 MHz, VRAM wait states |
| CRTC character | 1 µs, 2 bytes | 640 ns, 1 byte |
| Default line width | 80 bytes | 64 bytes |
| Default height | 200 lines | 240 lines |
| Video RAM | 16 KiB of main RAM | separate 16 KiB VRAM pages |
| 4-colour byte | mode 1 layout | identical layout to CPC mode 1 |
| 16-colour byte | mode 0, pens through palette | same bit positions, direct IGRB colour |
| Palette | 16 pens from 27 colours | 4 palette registers from 16 colours |
| Interrupts | 300 Hz from HSYNC count | CRTC cursor or sound timer |
| Sound | AY-3-8912, 3 channels | one divider channel and 4-bit amplitude |

See [tvc.md](tvc.md) for the TVC side.

## rtvc Coverage

`Cpc` boots the firmware to BASIC 1.0 and loads CDT tapes through the
firmware or custom loaders. It implements:

- RAM, ROM overlays, and Gate Array mode/ROM/pen/colour commands;
- the shared 6845 model in its type 0 variant, advanced once per µs;
- mode changes at HSYNC and palette writes at the beam position;
- the Gate Array interrupt counter and VSYNC resynchronisation;
- the 8255 and the AY register latch, far enough to read the keyboard;
- pulse-level cassette input and the motor relay;
- rtvc snapshots, breakpoints, stepping, and instruction tracing.

It does not implement AY audio, cassette output, disks, expansion ROMs,
RAM banking, other CRTC types, the printer port, or `.sna` snapshots.
Instruction times are rounded up to whole 4 T-state slots, so the cases
where real CPC timing differs from that rule run at the wrong speed.
Mode 3 is rendered like mode 2. Open work is tracked in [TODO.md](../TODO.md).

## Accuracy-Sensitive Behavior

- A default frame is 312 lines of 64 µs; timing must follow CRTC registers.
- Instruction times are aligned to 1 µs slots, not raw Z80 T-states.
- Interrupts come from the HSYNC counter, resynchronised by VSYNC; the
  acknowledge clears counter bit 5.
- Mode changes apply at the next HSYNC; palette changes apply immediately.
- Writes under an enabled ROM go to RAM, and video always reads RAM.
- Ports are decoded from individual high-byte address bits.
- Mode 0 and mode 1 pixel bits are interleaved, not packed left to right.
- Screen lines within a character row are `&800` apart.
- CRTC type differences matter for split-screen and overscan code.
