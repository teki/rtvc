# Zx82 Technical Reference

ZX Spectrum 48K hardware information for emulator authors and low-level
software developers.

`Zx82` is the rtvc development name for the initial ZX Spectrum target. This
document describes only the original 48K-class machine needed for
agent-assisted game conversion. It is not a specification for the Spectrum
128K family, Timex derivatives, peripherals, or a cycle-perfect preservation
emulator.

This is primarily an implementation-neutral description of the machine:
memory, I/O, frame timing, interrupts, video, keyboard, sound, and cassette
signals. The final sections define the intentionally smaller first Zx82 model,
including the decision not to emulate memory contention or general tape
waveforms.

## Technical Data

| Item | ZX Spectrum 48K value |
| --- | --- |
| CPU | Zilog Z80-compatible CPU |
| CPU clock | 3,500,000 Hz |
| CPU T-state | approximately 285.714 ns |
| CPU address space | Fixed 64 KiB |
| ROM | 16 KiB at `0x0000-0x3FFF` |
| RAM | 48 KiB at `0x4000-0xFFFF` |
| Video RAM | First 6,912 bytes of RAM |
| Video bitmap | 256 x 192, one bit per pixel |
| Attributes | 32 x 24 cells, one byte per 8 x 8 cell |
| Frame timing | 312 lines x 224 T-states = 69,888 T-states |
| Frame rate | approximately 50.08 Hz |
| Keyboard | 8 half-rows x 5 keys, active-low |
| Sound | One-bit internal speaker output |
| Cassette | Software-decoded EAR input and software-driven MIC/EAR output |
| Main custom logic | Ferranti ULA |

The Spectrum is small from the CPU's point of view: a fixed memory map and one
ULA I/O port family provide nearly all base-machine behavior.

## Machine Scope

The initial Zx82 machine is:

- a PAL ZX Spectrum 48K;
- one fixed 16 KiB ROM and 48 KiB RAM;
- the standard 256 x 192 bitmap and attribute display;
- the original keyboard matrix;
- the ULA border, speaker, and cassette bits;
- one maskable interrupt per video frame.

The first model does not include:

- Spectrum 16K as a separate configuration;
- Spectrum 128K, `+2`, `+2A`, or `+3` paging and sound hardware;
- Interface 1, Microdrives, disk drives, printers, or serial/network devices;
- Kempston, Fuller, or other joystick interfaces;
- AY-3-8912 sound;
- non-PAL or clone-specific timing.

These are separate machines or extensions rather than requirements for the
game-conversion workflow.

## Clock and Frame Timing

The CPU clock is the machine time base:

```text
CPU clock       3,500,000 Hz
scanline        224 T-states = 64 us
frame           312 lines
frame budget    69,888 T-states
frame rate      3,500,000 / 69,888 = approximately 50.08 Hz
```

Relative to the frame interrupt, the standard 48K display consists of:

```text
64 lines   before the active picture
192 lines  containing the active picture
56 lines   after the active picture
```

The first active bitmap byte is displayed 14,336 T-states, or 64 lines, after
the frame interrupt begins.

Each active line contains 256 picture pixels. The complete line also contains
border and horizontal-retrace time. Exact border raster placement matters to
software effects, but the initial Zx82 renderer may produce one completed
frame from memory rather than replaying every border change against the beam.

## Reset State

At reset:

- the Z80 begins from its normal reset state at `PC=0x0000`;
- the 16 KiB system ROM is visible at `0x0000-0x3FFF`;
- all 48 KiB of RAM remains mapped at `0x4000-0xFFFF`;
- no memory paging register exists;
- keyboard keys are released;
- no external cassette input is active;
- the frame timing starts from a deterministic phase.

Physical power-on RAM contents should not be relied upon. Zx82 may clear or
otherwise initialize RAM deterministically for repeatable tests and project
snapshots.

The ROM programs the normal display state during boot. Emulator-specific
border, speaker, and tape latch defaults should be deterministic, but software
should not use them as undocumented hardware guarantees.

## CPU and Bus Conventions

### Z80 use

The Spectrum does not modify the Z80 instruction set. Normal interrupt modes,
`HALT`, refresh-register behavior, and I/O semantics still apply.

### Port addresses

Z80 I/O operations expose a 16-bit address. The ULA responds whenever address
bit A0 is zero, so every even I/O address selects it. Software should normally
use low byte `0xFE`.

The high address byte is significant when reading the keyboard because bits
A8-A15 select keyboard half-rows.

### Byte order

The Z80 is little-endian. A 16-bit word at address `A` stores the low byte at
`A` and the high byte at `A+1`.

## Memory Map

The 48K map is fixed:

| CPU range | Size | Device | Access |
| --- | ---: | --- | --- |
| `0x0000-0x3FFF` | 16 KiB | System ROM | Read-only |
| `0x4000-0x57FF` | 6,144 bytes | Screen bitmap RAM | Read/write |
| `0x5800-0x5AFF` | 768 bytes | Screen attribute RAM | Read/write |
| `0x5B00-0x7FFF` | 9,472 bytes | Remaining lower RAM | Read/write |
| `0x8000-0xFFFF` | 32 KiB | Upper RAM | Read/write |

Writes to ROM have no effect.

There is no bank switching in the 48K machine. The first implementation
therefore needs only the currently mapped CPU address space in the debugger;
it does not need raw ROM-bank or RAM-bank addressing.

### Contended region

On hardware, `0x4000-0x7FFF` is shared with the ULA. The ULA can delay the CPU
while fetching display data. Some I/O operations are also delayed according
to the address and current raster position.

Zx82 deliberately omits these wait states. Reads and writes in
`0x4000-0x7FFF` take the Z80 core's ordinary timing, just like accesses to
upper RAM.

## I/O Map

### ULA port family

Every even I/O address selects the ULA. The canonical port is `0xFE`.

#### Write

```text
bit 7    unused
bit 6    unused
bit 5    unused
bit 4    EAR output and speaker level
bit 3    MIC output
bits 2-0 border color
```

The border color encoding is:

```text
bit 2  green
bit 1  red
bit 0  blue
```

The physical cassette and speaker circuit couples the MIC and EAR paths.
Zx82 may model bit 4 directly as the one-bit speaker and preserve bit 3 as a
cassette-output latch without reproducing board-revision analog behavior.

#### Read

```text
bit 7    1
bit 6    EAR cassette input
bit 5    1
bits 4-0 selected keyboard columns, active-low
```

Keyboard rows are selected by zero bits in A8-A15. If multiple rows are
selected, their five-bit values are ANDed.

### Unhandled ports

The real machine can expose ULA display fetches on otherwise undriven I/O
reads, commonly called the floating bus. The minimum Zx82 model returns
`0xFF` from unhandled odd ports and does not implement floating-bus behavior.

## Interrupt System

The ULA drives the Z80 maskable `/INT` input once per video frame. The frame
period is 69,888 T-states. Programs commonly use `HALT` or an interrupt
handler to synchronize work with the display.

The interrupt marks the timing origin used by this document:

```text
frame T-state 0       ULA requests the frame interrupt
frame T-state 14336   first active bitmap byte is displayed
frame T-state 69888   next frame interrupt
```

The ROM normally uses interrupt mode 1, which services the interrupt through
`0x0038`. Programs may select another Z80 interrupt mode, so Zx82 must retain
the CPU core's normal interrupt-mode behavior.

The initial implementation may represent the hardware pulse as one pending
maskable interrupt request per frame. Exact `/INT` pulse width and sub-
instruction sampling are deferred accuracy details, but there must never be
more or fewer than one frame request per 69,888 logical T-states.

Memory contention is not required for the interrupt schedule. It does affect
how many instructions real hardware completes between interrupts, so software
that depends on exact contended timing can drift relative to the Zx82 raster.

## Video System

### Display memory

The display uses 6,912 bytes:

```text
0x4000-0x57FF  6,144-byte monochrome bitmap
0x5800-0x5AFF    768-byte attribute array
```

The active picture is 256 x 192 pixels. Bitmap bytes are displayed most
significant bit first, so bit 7 is the leftmost pixel.

### Bitmap addressing

For pixel row `y` in `0..191` and byte column `x` in `0..31`:

```text
bitmap =
    0x4000
  | ((y & 0xC0) << 5)
  | ((y & 0x07) << 8)
  | ((y & 0x38) << 2)
  | x
```

The unusual arrangement groups the screen into thirds, then character rows,
then pixel rows within a character.

### Attribute addressing

Each attribute byte applies to one 8 x 8 pixel cell:

```text
attribute = 0x5800 + (y >> 3) * 32 + x
```

Its fields are:

```text
bit 7      FLASH
bit 6      BRIGHT
bits 5-3   PAPER color
bits 2-0   INK color
```

Color values use green, red, and blue bits in that order. A zero bitmap bit
selects PAPER and a one selects INK. BRIGHT selects the high-intensity palette
for both colors; bright black remains black.

When FLASH is set, INK and PAPER exchange roles every 16 frames. A complete
normal/inverted cycle therefore takes 32 frames.

### Border

The active picture is surrounded by the color selected through ULA output
bits 2-0. The real ULA can change the border during a scanline.

The minimum renderer may use a single border color for a completed frame.
Raster-accurate border stripes are optional and require recording port writes
against frame T-states.

## Keyboard

The keyboard is an active-low matrix of eight half-rows and five columns:

| Read address | Bit 0 | Bit 1 | Bit 2 | Bit 3 | Bit 4 |
| --- | --- | --- | --- | --- | --- |
| `0xFEFE` | Caps Shift | Z | X | C | V |
| `0xFDFE` | A | S | D | F | G |
| `0xFBFE` | Q | W | E | R | T |
| `0xF7FE` | 1 | 2 | 3 | 4 | 5 |
| `0xEFFE` | 0 | 9 | 8 | 7 | 6 |
| `0xDFFE` | P | O | I | U | Y |
| `0xBFFE` | Enter | L | K | J | H |
| `0x7FFE` | Space | Symbol Shift | M | N | B |

A pressed key reads as zero. A released key reads as one.

If several A8-A15 bits are low, Zx82 must AND the selected rows. This preserves
multi-row scans and the keyboard's normal matrix ghosting behavior.

Host key combinations for Spectrum keywords or shifted symbols are a UI
mapping concern. The emulated machine only receives matrix state.

## Sound and Cassette Interface

### Speaker

ULA output bit 4 drives the internal one-bit speaker path. A basic emulator can
convert changes in this bit into a bipolar or DC-filtered audio signal.

No programmable sound generator exists in the 48K machine.

### Cassette input

ULA input bit 6 exposes the EAR cassette signal. ROM and custom loaders measure
the time between transitions to decode tape data.

### Cassette output

ULA output bits 3 and 4 drive the cassette/speaker network. ROM save routines
toggle these outputs with software timing.

Issue 2 and Issue 3 machines differ in analog coupling and in the value read
back through EAR for some output combinations. These electrical differences
are not part of the minimum Zx82 model.

## Spectrum Tape Blocks

The standard ROM records a file as:

1. a 19-byte header block;
2. a variable-length data block.

Each logical block contains:

```text
flag byte
payload bytes
checksum byte
```

The flag is `0x00` for a header block and `0xFF` for a data block. The checksum
is chosen so XORing every byte in the block, including the flag and checksum,
produces zero.

The 17-byte header payload is:

| Offset | Size | Meaning |
| ---: | ---: | --- |
| 0 | 1 | Type: `0` program, `1` number array, `2` character array, `3` code |
| 1 | 10 | Filename, padded with spaces |
| 11 | 2 | Data length |
| 13 | 2 | Parameter 1 |
| 15 | 2 | Parameter 2 |

For a CODE file, parameter 1 is the saved start address. A `SCREEN$` file is a
CODE block with start address `0x4000` and length 6,912.

PROGRAM and array blocks require Sinclair BASIC loading semantics. Their
header fields are not a universal memory destination that can safely be used
for direct copying.

### Standard waveform

The standard ROM waveform uses:

| Part | Pulse length |
| --- | ---: |
| Pilot pulse | 2,168 T-states |
| Header pilot | 8,063 pulses |
| Data pilot | 3,223 pulses |
| First sync pulse | 667 T-states |
| Second sync pulse | 735 T-states |
| Zero bit half-pulse | 855 T-states |
| One bit half-pulse | 1,710 T-states |

Each data bit consists of two equal pulses and bytes are transmitted most
significant bit first.

These timings document the hardware-visible signal. The first Zx82 model does
not need to synthesize it if media is handled through an instant-load path.

## TAP Files

`.tap` is the simplest useful Spectrum tape container. It is a sequence of
logical blocks:

```text
u16 little-endian block length
block bytes
```

The block bytes are the flag, payload, and checksum described above. Timing is
implicitly the standard ROM timing.

TAP does not contain a destination address for every block. It preserves what
the ROM would receive from tape, not the behavior of the loader consuming it.

## TZX Files

TZX is a general tape-signal and tape-program container. Its ten-byte header
is:

```text
offset 0x00  "ZXTape!"
offset 0x07  0x1A
offset 0x08  major version
offset 0x09  minor version
```

The body contains ID-tagged blocks. Important examples are:

| ID | Meaning |
| ---: | --- |
| `0x10` | Standard-speed data |
| `0x11` | Turbo-speed data |
| `0x12` | Pure tone |
| `0x13` | Pulse sequence |
| `0x14` | Pure data |
| `0x15` | Direct recording |
| `0x18` | CSW recording |
| `0x19` | Generalized data |
| `0x20` | Pause or stop |
| `0x23` | Jump |
| `0x24`, `0x25` | Loop start and end |
| `0x26`, `0x27` | Call sequence and return |
| `0x28` | Selection menu |

An ID `0x10` standard-speed block contains:

```text
u16 pause after block, milliseconds
u16 data length
data bytes in TAP block form
```

TZX timing values use a 3.5 MHz Spectrum clock as their reference.

TZX is not generally suitable for blind memory injection. Turbo, pulse,
direct-recording, generalized-data, and control-flow blocks describe what a
tape player does. They do not describe the final memory map created by a
custom loader.

The first Zx82 media parser may support only ID `0x10`, normalized to the same
logical block representation as TAP. Other block IDs must produce a clear
unsupported-media result; they must not be silently treated as standard data.

## Instant Loading and Memory Injection

Directly copying every tape block into RAM is not generally correct:

- a standard CODE header can name a destination, but BASIC and array headers
  have different semantics;
- loaders can request only part of a block or load it at an address chosen at
  runtime;
- games often contain a BASIC loader followed by several machine-code blocks;
- custom loaders can use turbo timings, transform data, relocate it, or
  decompress it while loading;
- TZX control-flow blocks can replay, skip, loop, or select later blocks.

The practical agent-friendly choices are:

1. **Debugger or project-state injection.** Load a known memory image and CPU
   state directly. This is the simplest and most deterministic conversion
   workflow and requires no cassette implementation.
2. **Standard ROM-loader acceleration.** Detect a call into the selected
   Spectrum ROM's load routine, consume the next TAP or TZX `0x10` block, and
   reproduce that ROM routine's memory, register, flag, and return behavior.
   This avoids pulse emulation while remaining compatible with software that
   uses the ROM loader.
3. **Restricted CODE injection.** Parse a valid header/data pair and copy only
   a CODE payload to its declared address. This is useful as a tool command,
   but it does not run BASIC loaders and is not a general tape-load feature.

The recommended first Zx82 implementation is option 1, with option 2 added only
if ordinary tape images are needed. Full EAR waveform playback is outside the
initial scope.

ROM-loader acceleration must be associated with a verified ROM image or
signature. Entry addresses and exit effects should not be assumed to be
identical across arbitrary replacement ROMs.

## System ROM Placement

Zx82 requires one 16 KiB ZX Spectrum 48K ROM image:

```text
ROM file offset 0x0000-0x3FFF
CPU address     0x0000-0x3FFF
```

The ROM is always visible and is not paged. It must be supplied separately
from the emulator unless its distribution rights are established.

No raw ROM mapping interface is needed initially. Debugger reads through the
normal CPU map can inspect ROM bytes, and writes to that range are ignored by
the machine.

## Minimum Zx82 Model

A practical first implementation should:

1. run the reusable Z80 core at a 3.5 MHz logical clock;
2. provide a fixed 16 KiB ROM and 48 KiB RAM map;
3. issue one maskable interrupt every 69,888 T-states;
4. render the 256 x 192 bitmap, attributes, FLASH phase, and border;
5. implement even-port ULA decode and the eight-row keyboard matrix;
6. retain the speaker and cassette I/O bits in the ULA latch;
7. expose the mapped 64 KiB address space to the shared debugger;
8. support deterministic reset and project-state or snapshot restoration.

This is sufficient to boot the ROM, run ordinary 48K software already present
in memory, inspect and modify games through the debugger, send keyboard input,
and capture frames.

## Deliberately Omitted Behavior

The initial Zx82 implementation does not emulate:

- memory or I/O contention;
- floating-bus reads;
- ULA snow and refresh-register display corruption;
- scanline-accurate border changes;
- exact analog EAR/MIC feedback for different board revisions;
- exact cassette waveforms or custom tape loaders;
- tape saving;
- external peripherals and joystick interfaces;
- replacement ROM compatibility beyond normal mapped execution.

These omissions are deliberate. Zx82 is an agent-friendly Spectrum 48K target
for game conversion, not a comprehensive Spectrum preservation emulator.

## Accuracy-Sensitive Behavior

- A frame is 69,888 logical T-states, even though contention is omitted.
- The frame interrupt remains synchronized to that frame boundary.
- Bitmap addressing is non-linear; a linear 6,144-byte row-major renderer is
  incorrect.
- Attribute bytes are re-used for all eight pixel rows in a cell.
- FLASH swaps INK and PAPER every 16 frames.
- Every even I/O port selects the ULA, while keyboard row selection comes from
  the high address byte.
- Multiple selected keyboard rows are ANDed.
- Omitting contention changes instruction progress relative to the raster.
  Timing-sensitive loaders, border effects, multicolor effects, and some music
  routines can therefore fail or display differently.
- A TZX file is not a list of memory segments. Only explicitly supported
  standard blocks may be used by an instant loader.
